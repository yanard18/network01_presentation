The 4 Core Blocks of HTTP

The web ecosystem relies on four foundational building blocks:

BLOCK 1 Textual Format (HTML)

A textual format to represent hypertext documents: HyperText Markup Language (HTML).

BLOCK 2 Protocol (HTTP)

A standardized communication protocol to exchange these documents: HTTP.

BLOCK 3 Client (Web Browser)

A user-facing client application to display, render, and edit documents: Web Browser.

BLOCK 4 Server (httpd)

A server daemon to serve access to stored hypermedia documents: early version of httpd.

Protocol Characteristics

Stateless, but NOT Sessionless
  • HTTP is stateless — there is no direct connection state retained between two distinct requests.
  • However, it maintains sessions with the help of Cookies.
  • Allows websites to track login states and user activity across stateless calls.
HTTP is Extensible
  • Introduced in HTTP/1.0: HTTP Headers make the protocol effortless to extend.
  • New features, caching behavior, and security constraints can be added simply by defining new headers.
  • Maintains backward compatibility across protocol updates.

HTTP Origins & HTTP/0.9

1989 Tim Berners-Lee at CERN

In 1989, while working at CERN, Tim Berners-Lee wrote a proposal to build a hypertext system operating over the internet.

  • Laid the foundation for the World Wide Web.
  • Combined HTML, URI identifiers, and the HTTP protocol.
HTTP/0.9 The One-Line Protocol
  • Extremely simple protocol format.
  • Only supported the GET request method.
  • Had no version number, no headers, and no status codes.
HTTP/0.9 Request 
GET /my-page.html

HTTP/1.0 — Building Extensibility

HTTP/1.0 Key Features
  • Introduced protocol versioning in requests (e.g. HTTP/1.0).
  • Sent a status code line in responses (e.g. 200 OK).
  • Added the concept of HTTP Headers to both requests and responses.
  • Enabled transmission of non-HTML documents thanks to the Content-Type header.
HTTP/1.0 Request & Response Exchange 
GET /my-page.html HTTP/1.0
User-Agent: NCSA_Mosaic/2.0 (Windows 3.1)

HTTP/1.0 200 OK
Date: Tue, 15 Nov 1994 08:12:31 GMT
Server: CERN/3.0 libwww/2.17
Content-Type: text/html

HTTP/1.1 — Parallel TCP Connections

HTTP/1.1 Multi-Connection Architecture
  • Opens 6 different TCP connections to the server simultaneously.
  • Fault Tolerance: If 1 TCP connection is lost, the other 5 connections remain active.
  • Allowed parallel fetching of images, scripts, and stylesheets.
The Bottleneck / Problem

Problem: Opening 6 separate TCP connections is slow and resource-heavy.

  • High TCP handshake overhead (SYN, SYN-ACK, ACK per connection).
  • Network congestion and server socket exhaustion.

HTTP/2 — Greater Performance

SPDY FOUNDATION Origin

Web pages became complex (more visuals, larger data, higher traffic). Google created SPDY, serving as the foundation for HTTP/2.

FEATURES Key Improvements
  • Uses one single TCP connection.
  • Binary protocol rather than a text protocol.
  • Multiplexed parallel requests over the same connection.
  • Compresses headers to remove duplication (HPACK).
HTTP/2 Drawbacks
  • Head-of-Line (HOL) Blocking: Sending all data over one TCP connection means if 1 CSS packet drops, all other packets wait for it.
  • DoS Vulnerabilities: HTTP/2 suffers from DoS attacks because it relies on TCP stream management logic.

HTTP/3 — HTTP over QUIC

QUIC & UDP Transport Evolution
  • Uses QUIC instead of TCP.
  • QUIC is designed for lower latency for HTTP connections.
  • Operates on top of UDP.
SMART MANAGER How QUIC Works
  • QUIC makes UDP streams reliable.
  • It does not alter UDP itself; it creates a "smart manager" on top of it.
  • Lives directly in the web browser code.
  • Opens 1 connection, but builds completely different lanes (streams).

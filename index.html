What is HTTP?

HTTP (Hypertext Transfer Protocol) is an application-layer protocol designed to transfer hypermedia documents (HTML, JSON, binary streams) across distributed networks.

Client-Server

Operates via request-response cycles. Clients initiate HTTP requests; servers evaluate and return responses.

Stateless Design

Each request is processed independently. Servers do not natively retain client state without session tokens.

Layer 7 Protocol

Sits at Layer 7 of the OSI Model. Traditionally relies on TCP (Port 80/443), and modernly on UDP (QUIC Port 443).

Interactive Packet Inspector

Click tabs to inspect protocol primitives from a security perspective:

  • GET / HEAD: Read-only operations. Should never alter backend state (Risk: CSRF via GET).
  • POST / PUT / PATCH: State-changing operations. Require Strict CSRF Tokens & Input Validation.
  • DELETE / OPTIONS / TRACE: High risk if misconfigured! TRACE enables Cross-Site Tracing (XST).
  • 2xx Success (200 OK, 201 Created): Operational success.
  • 3xx Redirection (301 Moved, 302 Found): Target for Open Redirect vulnerabilities!
  • 4xx Client Errors (401 Unauthorized, 403 Forbidden, 404 Not Found): Must not leak sensitive stack debug info.
  • 5xx Server Errors (500 Internal, 502 Bad Gateway): Stack traces reveal code structure to attackers.
  • Host: Mandatory header in HTTP/1.1 (Target for Host Header Injection / Cache Poisoning).
  • Content-Length vs Transfer-Encoding: Used for payload sizing (Mismatches trigger HTTP Request Smuggling).
  • User-Agent & X-Forwarded-For: Client footprint headers (Easily spoofed in attacks).

Evolution of HTTP Versions

1991

HTTP / 0.9 (Raw ASCII)

One-line protocol: GET /index.html. No headers, no status codes, no encryption.

1996

HTTP / 1.0 (RFC 1945)

Introduced Key-Value Headers, Verbs (POST/HEAD), Status Codes, and Content-Types.

1997-2014

HTTP / 1.1 (RFC 2616 / 7230)

Persistent Connections (Keep-Alive), Chunked Transfer, Host Header (Virtual Hosting).

2015

HTTP / 2.0 (RFC 7540)

Binary Framing layer, Multiplexing over single TCP socket, HPACK Header Compression.

2022+

HTTP / 3.0 (RFC 9114)

QUIC Transport Protocol (UDP), Native TLS 1.3 Encryption, 0-RTT Connection Setup.

HTTP/0.9 & HTTP/1.0 Mechanics

HTTP/0.9 The Monolithic Beginning
  • Simple request format: GET /filename
  • Server returned raw HTML text and immediately closed connection.
  • No headers, no POST data, no status error reporting.
  • Security Impact: Zero authentication or integrity validation.
HTTP/1.0 Expandable Standard
  • Introduced Key-Value Metadata via Headers.
  • Added Status Codes (200, 404, 500) and MIME types.
  • Connection Overhead: Every single asset required a brand new TCP 3-Way Handshake (SYN, SYN-ACK, ACK).
  • Extremely slow for multi-asset web applications.

HTTP/1.1 & Head-of-Line Blocking

Key Innovations in HTTP/1.1
  • Keep-Alive Connections: Reuses a single TCP connection for multiple requests.
  • Virtual Hosting: Mandatory Host: header allowed multiple domains on 1 IP.
  • Chunked Transfer Encoding: Dynamic streaming without pre-calculating length.
Head-of-Line (HOL) Blocking

HTTP/1.1 serializes requests over TCP. If Request #1 stalls on the server (e.g. database lock), Request #2 and #3 are completely blocked!

REQ #1 [Slow DB Query] -------> (Blocks Socket)
REQ #2 [CSS File] -----------> [WAITING...]
REQ #3 [JS File] ------------> [WAITING...]

HTTP/2: Binary Framing & Multiplexing

Binary Framing Protocol

Replaces textual ASCII HTTP messages with discrete binary frames (HEADERS frame, DATA frame, RST_STREAM frame).

Multiplexed Streams

Multiple requests and responses are interleaved simultaneously over a single TCP connection, eliminating Application-layer HOL blocking!

HPACK Header Compression

Compresses redundant HTTP headers using indexed Huffman tables.

HTTP/1.1: 500-1000 Bytes per request header
HTTP/2 HPACK: ~20-50 Bytes per request header

Security Vulnerability: Shared compression state enabled attacks like CRIME & BREACH if TLS compression was misconfigured.

HTTP/3 & QUIC Transport Architecture

UDP + QUIC Transport Revolution
  • HTTP/3 drops TCP entirely in favor of QUIC over UDP (Port 443).
  • Eliminates TCP Transport-layer Head-of-Line Blocking (Packet loss on one stream does not freeze other streams).
  • Connection IDs: Allows seamless IP network roaming (e.g. WiFi to 5G without connection drops).
TLS 1.3 Native Security
  • TLS 1.3 is built directly into the QUIC handshake!
  • Encryption is mandatory — unencrypted HTTP/3 does not exist.
  • 0-RTT Connection Establishment: Allows instant resume of cryptographic sessions.

HTTP Cybersecurity Threat Vectors

Plaintext Sniffing

Standard HTTP transmits credentials, cookies, and tokens in cleartext over port 80. Susceptible to Wi-Fi sniffing and ARP Spoofing MITM attacks.

CRLF Injection

Inserting \r\n characters into user input breaks HTTP header boundaries, leading to HTTP Response Splitting & malicious header injection.

Session Hijacking

Missing cookie protection flags (HttpOnly, Secure) allows Cross-Site Scripting (XSS) to steal user session identifiers.

HTTP Request Smuggling (Desync)

Occurs when Front-End Proxies and Back-End Servers interpret HTTP request boundaries differently.

CL.TE Attack Payload Example 
POST / HTTP/1.1
Host: target.htb
Content-Length: 13
Transfer-Encoding: chunked

0

SMUGGLED POST /admin HTTP/1.1
Host: target.htb
Mechanism & Exploit Impact
  • CL.TE: Front-end uses Content-Length; Back-end uses Transfer-Encoding.
  • TE.CL: Front-end uses Transfer-Encoding; Back-end uses Content-Length.
  • Consequences: Bypass WAF controls, poison front-end web caches, steal victim request headers, or gain unauthorized admin privileges!

Protocol-Level Attack: HTTP/2 Rapid Reset

CVE-2023-44487 Record DDoS Vulnerability

Exploited HTTP/2 stream management logic to generate record-breaking DDoS attacks (>390 Million Requests Per Second).

  • Attacker sends HEADERS frame to open a stream.
  • Immediately sends RST_STREAM frame to cancel the stream.
  • Repeats billions of times in a tight loop over a single TCP socket.
root@htb:~# ./rapid_reset_exploit.py 
[Client] ---> HEADERS (Stream 1)   ---> [Server: Allocate Memory]
[Client] ---> RST_STREAM (Stream 1) ---> [Server: Cancel Processing]
[Client] ---> HEADERS (Stream 3)   ---> [Server: Allocate Memory]
[Client] ---> RST_STREAM (Stream 3) ---> [Server: Cancel Processing]
... (Repeat x 1,000,000 requests per socket)
Result: Server CPU & Thread Pool Exhaustion (DoS)

Securing Transport: HTTPS & TLS 1.3

TLS Cryptographic Protections
  • Confidentiality: Symmetric Encryption (AES-GCM, ChaCha20-Poly1305) prevents sniffing.
  • Integrity: HMAC / AEAD tags detect payload tampering.
  • Authentication: X.509 Certificates verify server identity.
  • Forward Secrecy: Ephemeral Diffie-Hellman (ECDHE) ensures compromised long-term keys cannot decrypt past traffic.
TLS 1.3 Handshake (1-RTT)

Essential Security Headers Hardening

HSTS Strict Transport Security
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

Forces browsers to interact with the domain exclusively over HTTPS, mitigating SSL Strip attacks.

CSP Content Security Policy
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.trusted.com

Restricts script execution sources to neutralize Cross-Site Scripting (XSS) and injection attacks.

Frame Options X-Frame-Options
X-Frame-Options: DENY

Prevents site embedding inside iframe tags to eliminate Clickjacking threats.

MIME Sniffing X-Content-Type-Options
X-Content-Type-Options: nosniff

Blocks browser MIME-type sniffing to prevent drive-by malware execution.

Secure Cookie Directives

Cookies represent session state in HTTP. Hardening cookie flags is a baseline defense:

Hardened Set-Cookie Header 
Set-Cookie: htb_token=s3cr3t_v4lu3; Secure; HttpOnly; SameSite=Strict; Path=/; Domain=secure.target.htb
Secure

Ensures cookie is ONLY transmitted over encrypted HTTPS connections.

HttpOnly

Blocks JavaScript access (document.cookie), protecting against XSS cookie theft.

SameSite=Strict

Prevents browser from sending cookies in cross-site requests (Mitigates CSRF).

Cybersecurity Hardening Checklist

Recommended Hardening Actions
  • Enforce HTTPS Everywhere with TLS 1.3 and HSTS Preloading.
  • Disable legacy protocols (HTTP/0.9, HTTP/1.0, SSLv3, TLS 1.0/1.1).
  • Deploy robust HTTP Security Headers (CSP, X-Frame-Options, Permissions-Policy).
  • Sanitize and normalize HTTP headers at Reverse Proxies to prevent Request Smuggling.
  • Rate-limit HTTP/2 RST_STREAM frames to mitigate Rapid Reset DDoS.
Common Anti-Patterns to Avoid
  • Transmitting sensitive credentials over unencrypted HTTP (Port 80).
  • Exposing server signature banners (e.g. Server: Apache/2.2.15).
  • Permitting wildcards in Access-Control-Allow-Origin: * with credentials.
  • Relying on client-side state without cryptographic signature verification.
